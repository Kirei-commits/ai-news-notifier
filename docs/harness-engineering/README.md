# ハーネスエンジニアリング 学習計画

## ハーネスとは

LLM そのものではなく、**LLM を仕事に使えるようにする周辺すべて**のこと。

```
        ┌─────────────────────────── ハーネス ───────────────────────────┐
入力 →  │ プロンプト構築 → ループ制御 → ツール実行 → 結果整形 → 停止判定 │ → 成果物
        │        ↑                                          ↓            │
        │     コンテキスト管理 / 権限ゲート / トレース / 評価            │
        └────────────────────────────────────────────────────────────────┘
                                    ↕
                                  モデル
```

モデルの質が同じでも、ハーネスの質でエージェントの実用性は 10 倍変わる。
Claude Code も Cursor も Devin も「ハーネスが製品」であって、モデルは共通部品でしかない。

## 学び方の方針

1. **ライブラリを使わずに一度自分で書く。** LangChain 等を最初に使うと、一番学ぶべき層が隠れる。
2. **このリポジトリを題材にする。** RSS 収集 → 選別 → 翻訳 → Discord 投稿 という
   「取ってくる / 判断する / 副作用を起こす」が全部揃った実タスクなので教材として都合が良い。
3. **各フェーズは「動くコード + テスト」で終える。** 読んだだけのものは身についていない扱いにする。

## Phase 0 — LLM API の素の形

**学ぶこと**

- `messages` は状態を持たない。毎回全履歴を送っている。
- `role` は `user` / `assistant` の 2 つだけ。ツール結果も「user の発言」として送る。
- `stop_reason` がループ制御の心臓部（`end_turn` / `tool_use` / `max_tokens` / `refusal`）。
- `usage` が唯一の実測値。トークン数を推測で語らない。

**なぜ重要か**

ハーネスのバグの大半は「モデルに何を送ったか分かっていない」ことに起因する。
SDK の便利メソッドから入ると、この層が見えないまま積み上げることになる。

**実装課題**

- プロバイダ非依存の内部表現（`Message` / `ContentBlock` / `ModelResponse`）を定義する。
- Anthropic / Gemini / モック の 3 実装をその内部表現に変換する。

**完了条件**

- プロバイダを差し替えてもループ側のコードが 1 行も変わらない。

## Phase 1 — エージェントループ

**学ぶこと**

エージェントの本体はこれだけ:

```
messages = [user(入力)]
loop:
  res = model(system, messages, tools)
  messages += assistant(res.content)
  if res.stopReason != "tool_use": break
  results = 各 tool_use を実行
  messages += user(results 全部を 1 メッセージで)
```

**落とし穴（全部このリポジトリで踏んで確認する）**

- ツール結果を複数メッセージに分けて送ると、モデルが並列ツール呼び出しをやめる。**必ず 1 メッセージ**にまとめる。
- ツールが例外を投げたらループを落とすのではなく、`is_error` 付きの結果としてモデルに返す。モデルは自己修復できる。
- 未知のツール名も落とさずエラー結果で返す。
- 無限ループ対策の `maxTurns` は必須。停止理由を型で表現する（`done` / `max_turns` / `aborted` / `error`）。

**完了条件**

- モックプロバイダで「2 回ツールを呼んでから終了する」シナリオがテストで再現できる。

## Phase 2 — ツール設計

**学ぶこと**

ツールは「関数」ではなく **モデルへの UI** である。名前・説明・スキーマ・エラー文言のすべてがプロンプトの一部。

- スキーマは JSON Schema。TypeScript の型と二重管理にしないこと。
- 入力検証は必須。モデルは平気で型を外す。検証エラーは「何が間違っていて、どう直すか」をモデルに返す。
- **出力サイズの制御がツール設計の 8 割。** RSS 全文をそのまま返すとコンテキストが即死する。
- 副作用のあるツール（Discord 投稿）と読み取り専用ツールを型で区別する。

**完了条件**

- スキーマ定義から JSON Schema と TS 型と実行時バリデータが 1 箇所から導出される。

---

## Phase 3 — コンテキストエンジニアリング

**学ぶこと**

- コンテキストは予算。何トークン使ったかを常に計測する。
- 削り方の優先順位: 古いツール結果 > 古い thinking > 古い会話 > システムプロンプト。
- 3 つの手法の違いを理解する: **切り詰め (truncate)** / **消去 (context editing)** / **要約 (compaction)**。
- システムプロンプトは安定部分を先頭に置く（プロンプトキャッシュは前方一致）。

**実装課題**

- `estimateTokens` と予算チェックをループに組み込む。
- 閾値超過時に古いツール結果を「(省略: N 文字)」に置換する戦略を実装。
- 要約戦略（別モデル呼び出しで履歴を圧縮）を実装し、切り詰めと比較する。

---

## Phase 4 — 権限と安全

**学ぶこと**

- 副作用を「読み取り / 冪等な書き込み / 不可逆」に分類する。
- 承認ゲートはツール実行の**直前**に挟む。モデルの申告を信用しない。
- `dry-run` は機能ではなくデフォルト。実投稿は明示的なフラグでのみ。
- プロンプトインジェクション: RSS のタイトルは**第三者が書いた文字列**。ツール結果をそのまま指示として扱わない設計にする。

**実装課題**

- `PermissionDecision = allow | deny | ask` を返すゲートをループに挟む。
- `post_discord` を既定 deny にし、`--allow-post` で解禁する。

---

## Phase 5 — 観測性

**学ぶこと**

- 構造化トレース（JSONL）が無いエージェントはデバッグ不能。
- 記録すべきは「モデルに送った全文」と「モデルが返した全文」。要約したログは役に立たない。
- コスト会計は `usage` の積算で行う。
- **リプレイ**: 記録したトレースからモデル応答を再生できると、ハーネス側の変更を API 無しでテストできる。

**実装課題**

- `.harness/traces/<runId>.jsonl` への書き出し。
- トレースを食わせて動く `ReplayProvider`。

---

## Phase 6 — 評価 (Evals)

**学ぶこと**

- エージェントの改善は評価なしには不可能。「なんとなく良くなった」は退行を隠す。
- 評価の 3 型: **決定的アサーション**（最も価値が高い）/ **LLM judge** / **人手**。
- 測る対象はハーネスの挙動: ターン数、ツール呼び出し回数、コスト、成功率。
- フレーキーさは温度だけでなくツール順序にも由来する。

**実装課題**

- `evals/cases/*.ts` にタスクを定義し、`npm run eval` で一括実行・スコア表示。

---

## Phase 7 — 拡張機構

**学ぶこと**

- **サブエージェント**: 親のコンテキストを汚さずに探索させる。返すのは結論だけ。
- **フック**: ツール実行の前後に決定的な処理を差し込む（lint、検証、記録）。
- **スキル / 段階的開示**: 全知識をシステムプロンプトに入れず、必要になった時に読ませる。
- 並列実行と、それを壊さないための結果の返し方。

---

## Phase 8 — 運用

**学ぶこと**

- リトライは指数バックオフ + ジッタ。429 は `retry-after` を尊重する。
- プロンプトキャッシュはコストの支配項になりうる。キャッシュヒット率を計測する。
- 冪等性キー。GitHub Actions で二重起動しても二重投稿しない設計。
- 失敗時の可観測性（どのターンで落ちたかが分かること）。
